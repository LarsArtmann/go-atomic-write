02Partially Done

Windows durability — directory fsync is a no-op

File-level durability is handled: file.Sync() on Windows calls FlushFileBuffers, which flushes the file's data to disk. However, there is no POSIX-equivalent directory fsync on Windows — the directory entry after rename is not explicitly synced. This is a known platform limitation, documented in AGENTS.md, but not yet tested on an actual Windows machine.

Status: Code written and compiles via build tags. Untested on actual Windows hardware.

The original plan included a Write benchmark to measure fsync overhead vs the old no-fsync path. Not yet written — benchmarks for xxhash vs SHA-256 exist but no end-to-end Write benchmark exists.

Stale temp file cleanup

Unique temp names prevent concurrent corruption, but if a process crashes mid-write, the .tmp file remains forever. No cleanup-on-startup logic exists yet. With unique names, stale files don't interfere with new writes, but they accumulate.

context.Context support

Write() blocks on fsync, which can take unbounded time on slow/network filesystems. No context.Context parameter exists for cancellation or timeout. This is a design decision, not an oversight — see #1 Open Question.

04Totally Fucked Up!

Fixed

The .bak dance broke POSIX atomicity

atomicwrite.go:114-122 (old code)

The original atomicRename did os.Rename(path, path+".bak") then os.Rename(tmpPath, path). On POSIX, a single rename(2) atomically swaps the inode — readers always see either old or new content, never ENOENT. Splitting into two renames opened a window where path didn't exist. A concurrent reader (or a crash between the two calls) saw the file missing. The library named "atomic-write" was not atomic.

Fix: Single os.Rename(tmp, path) — one atomic syscall on POSIX.
Fixed

Concurrent writers corrupted the shared .tmp file

atomicwrite.go:73 (old code, tmpPath := path + ".tmp")

tmpPath was computed before the lock. Two Write() calls to the same target both opened/truncated/wrote the same path.tmp, interleaving bytes. The lock only guarded the verify+rename, not the staging write. The winner then renamed a possibly-corrupted file.

Fix: Unique temp file names via crypto/rand — each writer gets path + "." + randomHex + ".tmp".
Fixed

The concurrency test couldn't catch the corruption bug

atomicwrite_test.go:254 (old code)

TestConcurrentWriteRACE used identical content ("updated") from all 5 goroutines. Even if bytes were interleaved, the result was the same string — the test would pass on corrupted data. The test was structurally incapable of detecting the bug it was supposed to guard against.

Fix: 10 writers with divergent content (writer-0 – writer-9) + integrity check verifying the final file is exactly one writer's payload.

05What We Should Improve

Test on actual Windows

rename_windows.go compiles via build tags but has never run on a real Windows machine. The retry loop, ERROR_ACCESS_DENIED detection, and MoveFileEx behavior are all unverified.

Stale temp file accumulation

Crashed writes leave .tmp files forever. Unique names prevent interference but don't clean up. Need a glob-and-remove on startup, or document the expected cleanup pattern.

No Write benchmark

fsync adds real latency. We should benchmark Write end-to-end to quantify the cost and establish a regression baseline.

No fuzz tests

writeAndSync and randomSuffix handle arbitrary data sizes and edge cases. Fuzz testing would catch panics or data corruption on unusual inputs (empty data, very large data, concurrent access).

No godoc examples

ExampleWrite, ExampleFingerprintFile etc. would make the package discoverable via go doc and pkg.go.dev.

Windows durability gap

No directory fsync equivalent on Windows. The rename directory entry may not be durable after a crash. Should be documented as a known limitation, or addressed via MOVEFILE_WRITE_THROUGH.

07#1 Open Question

Should Write() accept a context.Context?

Write() now calls file.Sync(), which flushes to disk. On a local SSD this takes microseconds. On a network filesystem (NFS, SMB, CephFS) or a slow disk, fsync can take seconds or even minutes. There is no way for a caller to cancel or timeout a write.

Adding context.Context is an API change. Go's convention is ctx as the first parameter (Write(ctx, path, data, fp)), which breaks every existing call site. Alternatively, a new function WriteContext could be added alongside the existing Write.

The deeper question: does fsync even respect context? file.Sync() calls fsync(2), which is a blocking syscall with no cancellation primitive. A context-based timeout would need to run the write in a goroutine and abandon it on timeout — leaving the temp file on disk. That's a leak, not a clean cancel.

Why I can't figure this out myself: This is a product decision, not a technical one. It depends on who the callers are and whether they run on local disks (no timeout needed) or network filesystems (timeout critical). I don't know the deployment context.
